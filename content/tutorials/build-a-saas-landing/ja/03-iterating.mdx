Step 02 のプロンプトを実行して Hero が返ってきた。<strong>惜しい</strong>——
見出しは決まっていて、パレットは正しく、CTA はちょうど 1 つ——だが
1 つだけおかしい。サブ見出しがマーケティングの埋め草に読めるかもしれない。
CTA の色がアクセントと喧嘩しているかもしれない。全体が窮屈に感じるかもしれない。

この瞬間の本能は作り直すことだ：もう一度プロンプトを実行して期待する。
<strong>やめること。</strong> このステップのスキルは<em>外科手術的な後続</em>だ——
間違った 1 つを直し、正しい 4 つに触れない<strong>最小のプロンプト</strong>。

## まず「その 1 つ」を名指しする

後続プロンプトの 1 文字を書く前に、1 文を書く：

> 唯一おかしいのは ______ だ。

その文を 1 つの節で終えられないなら、まだ反復する準備ができていない。
それは問題が 1 つではなく<strong>複数</strong>あるということだ——そしてそれらを
1 つの後続にまとめることが、すでに機能している部分を失う原因になる。
<strong>1 度に 1 つ、大きいものから直す</strong>。

## プロンプトを書く前に診断する

ほぼすべての「おかしい」Hero は、次の 5 つの次元のうち<strong>ちょうど 1 つ</strong>で
おかしい。何かを書く前に、どれかを見つける：

<Checklist
  storageKey="saas-landing-step-03-diagnose"
  title="どの単一次元がおかしいか？"
  items={[
    { id: 'content', label: 'コンテンツ——言葉が汎用的、または間違ったことを言っている' },
    { id: 'layout', label: 'レイアウト——部分は良いが構成がおかしい' },
    { id: 'colour', label: 'カラー——何かがパレットと喧嘩している、またはコントラストが間違っている' },
    { id: 'type', label: 'タイポ——選んだスタイルに対してウェイト・サイズ・組み合わせが間違っている' },
    { id: 'spacing', label: '間隔——詰まりすぎ、緩すぎ、またはリズムが不揃い' }
  ]}
/>

肝心なのは次元を<strong>声に出して名指しする</strong>ことだ。「おかしく見える」では
動けない。「サブ見出しが汎用的だ」なら動ける。<strong>診断が狭いほど、後続は
小さく——そして信頼できる</strong>。

## 後続プロンプトの形

<Callout tone="info" title="手で直す方がプロンプトより速いとき">
  すでに直し方が見えている 1 行のコピー変更なら、構造化プロンプトを
  書くより<strong>ファイルを手で編集する方が速い</strong>。変更がビジュアルで、
  一度に複数の要素にまたがり、または自分でも直し方がまだ見えない
  ——つまり本来なら作り直すような場合——にだけ後続プロンプトに手を
  伸ばす。下記の形はそうした場合のためのものだ。
</Callout>

良い後続には、最初のプロンプトになかった 2 つのブロックがある：明示的な
<strong>Keep（保持）</strong>リストと、項目 1 つだけの <strong>Change（変更）</strong>。
Keep ブロックこそが全体の仕掛けだ——モデルに<strong>何を再生成しないか</strong>を伝える。

<CodeBlock
  title="外科手術的な後続プロンプト"
  language="text"
  code={`Hero は惜しい。1 つの変更を除き、すべてそのまま保持する。

# 保持（触れない）
- 見出しのコピー、書かれた通りそのまま
- 唯一の CTA、そのラベルと位置
- パレットとアクセントカラー
- 全体のレイアウトと垂直方向の間隔

# 変更（これだけ）
サブ見出しが汎用的だ。このオーディエンスが得る具体的な成果を名指しする
ように書き直す。平易な言葉で、最大 18 語。見出しの言い換えにしないこと。
他は何も変えない。

# 出力
同じファイル app/(marketing)/page.tsx を返す。上記の変更に必要な
diff だけ。無関係なコードをリファクタリングしない、何もリネームしない、
頼んでいない部分を「改善」しない。`}
/>

`# 保持` ブロックは冗長に見える——モデルはファイルを見られるのに、なぜ
良い部分を言い直す？ なぜなら、アンカーなしで「サブ見出しを直して」と
渡されたモデルは、喜んで見出しも書き直し、ボタンのスタイルを差し替え、
「ついでに」セクション全体の間隔を取り直すからだ。Keep リストは柵だ。
<strong>爆発半径を制約する</strong>。

## 「何を変えるか」を具体的に書く

上記の Change 行はコピーを指定している——言葉にしやすい次元だ。それが
生んだ before/after はこうだ：

> <strong>変更前：</strong>ワークフローを効率化しチームをスケールさせる
> オールインワンプラットフォーム。
>
> <strong>変更後：</strong>月末決算を 5 日から 1 日に短縮する。

変更後は具体的な成果と数字を名指ししている。変更前はどの SaaS にでも
貼り付く。「オーディエンスに具体的」とは、助言ではなく実際のテキストに
なったときこう見える、ということだ。

ビジュアル次元は難しい。<strong>レンダリングされた結果</strong>を言葉ではなく
描写するからだ。対処法は、形容詞ではなく<strong>測定可能なターゲット</strong>に
変更を錨付けることだ：

<CodeBlock
  title="ビジュアル次元の Change 行"
  language="text"
  code={`# 間隔——詰まりすぎ
Hero が窮屈に感じる。見出し、サブ見出し、CTA の間の垂直方向の間隔を
それぞれ 24px と 32px に増やす。他は何も変えない。

# カラー——CTA がアクセントと喧嘩
CTA が見出しと注目を奪い合っている。CTA をアクセントカラーのフル
彩度にし、見出しをパレットのインクカラーに落ち着かせる。他は何も変えない。`}
/>

「詰まりすぎ」は Change 行ではない。「間隔を 32px に増やす」が Change 行だ。
<strong>ターゲットが測定可能なほど、モデルが推測する diff は小さくなる</strong>。

## 1 ラウンドに 1 変更

後続の形を覚えると、まとめたくなる：サブ見出し<strong>と</strong> CTA の色
<strong>と</strong>間隔を 1 つのプロンプトで全部直す。抵抗すること。

<Callout tone="warn" title="まとめて直すと、デバッガを失う">
  3 つの変更を一度に頼んで結果が悪くなったとき、3 つの指示のどれが
  退行を引き起こしたか分からない。1 ラウンドに 1 変更なら、すべての
  反復が<strong>帰属可能</strong>になる——何が動いたか常に正確に分かる。遅く
  感じる。実際にははるかに速い。複数変更が絡んだ混乱をほどく必要が
  決してないからだ。
</Callout>

## 後続のあとの受け入れチェック

モデルは diff を返さない——1 行だけ触れと頼んでも、<strong>ファイル全体を
書き直して返す</strong>。だからあなたは「1 バイト単位の一致」を確認している
<strong>のではない</strong>：それはほぼ成立せず、追いかけると作り直しループに
真っ直ぐ戻る。確認するのはアンカーが<strong>読んでも見ても同じか</strong>だ。
目で追う：

<Checklist
  storageKey="saas-landing-step-03-output"
  title="後続は本当に機能したか？"
  items={[
    { id: 'fixed', label: '名指しした 1 つが今は直っている' },
    { id: 'headline', label: '見出しが同じに読める——同じ言葉、同じ意味' },
    { id: 'cta', label: 'CTA のラベル・スタイル・位置が変わっていない' },
    { id: 'palette', label: 'パレットとアクセントカラーが変わっていない' },
    { id: 'layout', label: 'レイアウトと間隔が同じに見える' }
  ]}
/>

見た目だけのゆらぎは無視する——行の折り返し直し、import の並べ替え、
引用符スタイルの違い。重要なのは、アンカーが<strong>見える・読める</strong>形で
変わったかだ：見出しが言い換えられた、ボタンが動いた、アクセントが
ずれた。1 つでもあれば、その後続は<strong>失敗</strong>だ——進歩に見えても。
より硬い Keep ブロックで再実行するか、戻して Change の 1 行を絞る。
<strong>アンカーをこっそり壊した修正を受け入れないこと</strong>。その負債は後の
すべてのセクションで複利で増える。

## なぜこの形は汎化するのか

<strong>Keep / Change</strong> 構造は、Step 02 の <strong>ロール / 決定 / タスク /
制約 / 出力</strong> の反復版の対応物だ。すでにほぼ正しいセクションに触れる
たび——価格、FAQ、Step 04 の機能グリッド——同じ 2 つのブロックに手を
伸ばす：機能するものをアンカーし、1 つの変更を名指しし、diff を制約する。

ここで身についているスキルは「AI 出力を反復する」ことでは<strong>ない</strong>。
それは<strong>爆発半径を制約し、反復が常に 1 つだけを動かすようにする</strong>ことだ。
