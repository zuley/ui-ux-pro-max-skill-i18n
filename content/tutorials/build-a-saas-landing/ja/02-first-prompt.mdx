Step 01 を終えて、5 行のメモができた：オーディエンス、感情、
スタイル、パレット、3 つの禁止事項。次はこのメモを
<strong>最初の本物のプロンプト</strong>——ランディングページの Hero セクションを
生成するもの——に変える。

ここでは意図的に Hero だけから始める。モデルに「ランディングページを
デザインして」と一度に頼むのは、スロップに戻る最速の方法だ。
<strong>すでに下した決定を組み込んだ 1 つのセクション</strong>を頼むのが、
そこから抜け出す最速の方法だ。

## このステップで作るもの

スクリーンショットに撮りたくなる Hero セクション。具体的には：

- <strong>あなたの</strong>プロダクトらしく聞こえる見出し——「ワークフローを変える」ではなく
- 1 文のサブ見出し——3 行の機能説明ではなく
- 単一のプライマリ CTA（「詳しく見る」のセカンダリはなし）
- Step 01 のスタイル＋パレットと一致するビジュアル処理

それだけ。機能グリッドも、ロゴ帯も、証言もない。それらは後のステップで来る。

## 機能するプロンプトの構造

本当に保存したくなる Hero を生成するプロンプトには、
ほぼ同じ順序で同じ 5 つのセクションが含まれている。この形を暗記する——
次のステップのすべてのセクションで再利用する：

<Checklist
  storageKey="saas-landing-step-02"
  title="Hero プロンプトの 5 つのセクション"
  items={[
    { id: 'role', label: 'ロール行——モデルに何になってほしいかを伝える（1 文）' },
    { id: 'decisions', label: '決定の入力——Step 01 の 5 行メモをそのまま貼る' },
    { id: 'task', label: 'タスク——1 つの Hero セクション。ページ全体ではない。' },
    { id: 'constraints', label: '制約——禁止リストを言い直したもの' },
    { id: 'output', label: '出力形式——具体的にどのファイル、どのスタック' }
  ]}
/>

最もよくある間違いは、<strong>タスク</strong>を間違った場所に置くことだ。
「Hero を作って」と先に書き、後から制約を並べる人が多い。
モデルは最初に読んだものを重力の中心として扱う——だから最初に
読むべきは<strong>あなたが何を頼んでいるか</strong>と
<strong>すでに決まっていること</strong>であって、タスクではない。

## 実際のテンプレート

これをコピーする。Step 01 から来た 5 行を置き換える：

<CodeBlock
  title="Hero セクションプロンプト"
  language="text"
  code={`あなたは SaaS ランディングページを構築しているシニアプロダクトデザイナーだ。
このプロジェクトのビジュアル決定はすでに下されている——あなたの仕事は
それらを実行することであって、再決定することではない。

# 決定（固定済み）
オーディエンス：<Step 01 の 1 文>
最初の 2 秒での感情：<Step 01 の 1 つの形容詞>
スタイル：<50 スタイルの名前、例："Editorial Brutalist">
パレット：<21 パレットの名前、例："Slate Ink">
禁止：<Step 01 の 3 つ>

# タスク
ランディングページの Hero セクションを構築する。Hero だけ——機能グリッドも、
ロゴ帯も、証言も、フッターも不要。1440px 幅の画面でビューポートに
収まる 1 つのセクション。

Hero には以下が含まれること：
- 1 つの見出し（1〜2 行、最大約 10 語）。見出しは汎用的な SaaS の
  定型句ではなく、このオーディエンス向けに書かれたように読めること。
  「ワークフローを変える」「モダンなチームのために作られた」は禁止。
  上記のオーディエンスに対して具体的に。
- 1 つのサブ見出し（1 文、最大 18 語）。誰のためのもので何をするか、
  平易な言葉で説明する。
- 1 つのプライマリ CTA（ボタン 1 個）。「詳しく見る」のセカンダリリンクは不要。
- 上記のスタイル＋パレットと一致するビジュアル処理。

# 制約
- 禁止リストを容赦なく適用すること。デフォルトが禁止事項に
  当たる場合は、次善の代替を選ぶ。
- 見出しがページ上で最も大きく主張すること。他のすべては引く。
- グラデーション背景は禁止。3 列カード行は禁止（それは後のセクション、
  Hero ではない）。
- システム間隔を使うこと：8px ベース、垂直リズムはすべて 24px の倍数。

# 出力
ファイル 1 つを出力：app/(marketing)/page.tsx
スタック：Next.js 15 App Router、React Server Components、Tailwind v4。
このファイルにクライアントコンポーネントは不要。Tailwind 以外の
外部依存は不要。SVG はすべてインライン。`}
/>

1 つのセクションにしては大量のプロンプトに見える。その通りだ。
理由は、<strong>プロンプト内のすべての要素が、なければ何度も作り直す
ことになる決定</strong>だからだ。決定を前に積み込むことが、
4 回作り直すことなく最初の出力で保存できる Hero を得るための方法だ。

## 良い出力はどう見えるか

このプロンプトを実行したとき、出力はこれらすべてに「はい」と
答えるべきだ：

<Checklist
  storageKey="saas-landing-step-02-output"
  title="最初の Hero の受け入れチェック"
  items={[
    { id: 'specific', label: '見出しがオーディエンスに対して具体的な何かに言及している——「チーム」や「ワークフロー」ではなく' },
    { id: 'one-cta', label: 'ボタンがちょうど 1 つある、2 つではなく' },
    { id: 'palette', label: 'アクセントカラーが指定したパレットと目に見えて一致している' },
    { id: 'style', label: 'ビジュアル処理が指定したスタイルと一致している（セリフ vs サンセリフ、非対称 vs センタリングなど）' },
    { id: 'no-slop', label: '3 つの禁止事項が出力に現れていない' }
  ]}
/>

5 つのうち 4 つに「はい」と答えられるなら、このドラフトを Step 03 に進める。
<strong>2 つ以上に「いいえ」</strong>なら、作り直さないこと——プロンプトのどのセクションが
曖昧だったかを振り返る。ほぼ常に答えは<strong>決定</strong>ブロックが汎用すぎたことにある。
1 行を絞り込んで再実行する。

<Callout tone="warn" title="何も変えずに再生成しないこと">
  同じプロンプトを再実行してより良い結果を期待するのは、
  AI との作業で最もコストがかかる失敗モードだ。出力が気に入らなければ、
  プロンプトを変える。出力が惜しいが 1 つの次元で間違っているなら、
  <strong>その次元に対処するようプロンプトを編集してから</strong>再実行する。
  盲目的に再実行しない。
</Callout>

## なぜこの形は汎化するのか

5 つのセクション構造——<strong>ロール、決定、タスク、制約、出力</strong>——は
Step 03〜05 のすべてのセクションで使う形と同じだ。これを内面化すれば、
価格セクションや FAQ セクションのプロンプトを書くのは 3 分の作業になる：
決定ブロックはそのまま、タスクと制約を入れ替えて、再実行する。

ここで身についているスキルは「良いプロンプトを書く」ことでは<strong>ない</strong>。
それは<strong>プロンプトの仕事を減らすために決定を前に積み込む</strong>ことだ。
