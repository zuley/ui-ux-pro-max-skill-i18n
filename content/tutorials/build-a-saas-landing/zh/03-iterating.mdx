你跑完了 step 02 的 Prompt，拿到一个 Hero。它**很接近了**——标题立住
了、配色对、CTA 正好一个——但有一处不对。可能副标读起来像营销废话，
可能 CTA 颜色和主色打架，可能整个看着挤。

这个时候的本能是重摇：再跑一遍 Prompt，碰运气。**不要这么干。** 这一
步要练的技能是*外科手术式的后续*——用**最小的 Prompt** 去修那一处不对
的，同时**一点不碰**那四处对的。

## 先把「那一处」说清楚

在你敲下后续 Prompt 的第一个字之前，先写一句话：

> 唯一不对的是 ______。

如果你没法用一个分句把这句话写完，那你还没准备好迭代。这说明你有**好
几个**问题，不是一个——而把它们打包进一个后续 Prompt，正是你把已经对
的部分搞砸的方式。**一次修一个，从最大的那个开始**。

## 动手之前先诊断

几乎每一个「不对」的 Hero，问题都恰好落在下面五个维度里的**某一个**
上。在你写任何东西之前，先找出是哪一个：

  storageKey="saas-landing-step-03-diagnose"
  title="是哪一个维度出了问题？"
  items={[
    { id: 'content', label: '内容——文字太泛，或者说错了话' },
    { id: 'layout', label: '布局——局部还行，但整体构图不对' },
    { id: 'colour', label: '颜色——有东西和配色打架，或者对比度不对' },
    { id: 'type', label: '字体——字重、字号或搭配不符合你选的风格' },
    { id: 'spacing', label: '间距——太挤、太松，或者节奏不一致' }
  ]}
/>

关键是把维度**说出口**。「看着不对」没法动手。「副标太泛」可以。**诊断
越窄，后续 Prompt 就越小——也越可靠**。

## 后续 Prompt 长什么样

<Callout tone="info" title="什么时候手改比写 Prompt 快">
  如果是一处你已经能想清楚怎么改的单行文案，**直接手动改文件比写一个
  结构化 Prompt 更快**。当改动是视觉的、一次牵动好几个元素、或者你自
  己都还想不出怎么改——也就是那些你本来会去重摇的情况——才动用后续
  Prompt。下面这个形状是为这些情况准备的。
</Callout>

一个好的后续，比第一个 Prompt 多了两块：一块明确的 **Keep（保留）**
清单，和一块只有一项的 **Change（修改）**。Keep 这一块才是整个诀窍
——它告诉模型**哪些不要重新生成**。

<CodeBlock
  title="外科手术式后续 Prompt"
  language="text"
  code={`这个 Hero 很接近了。除了一处改动，其他**全部原样保留**。

# 保留（不要碰）
- 标题文案，一字不改
- 那个唯一的 CTA，它的文字和位置
- 配色和主色
- 整体布局和垂直间距

# 修改（只改这个）
副标太泛。重写它，让它说清楚**这个受众**具体能拿到什么结果，用人话，
最多 18 个词。不能是标题的复述。**其他一律不动**。

# 输出
返回同一个文件 app/(marketing)/page.tsx，只带上面那处改动需要的
diff。不要重构无关代码，不要重命名任何东西，不要「顺手优化」我没
问到的部分。`}
/>

`# 保留` 这一块看着多余——模型能看到文件，为什么还要把好的部分再写
一遍？因为一个被丢了句「修一下副标」、又没有锚点的模型，会很开心地
把标题也重写了、把按钮样式换了、把整个 section 的间距「顺便」重排一
遍。Keep 清单是一道围栏。**它框住了爆炸半径**。

## 把「改什么」写具体

上面那条 Change 改的是文案——最容易用文字说清的维度。它产出的
before/after 长这样：

> **改之前：**一站式平台，让你的工作流更顺畅、团队更易扩展。
>
> **改之后：**把月末结账从 5 天压到 1 天。

「改之后」点名了一个具体结果和一个数字；「改之前」粘到任何一家 SaaS
上都成立。这就是「具体到受众」落成真实文案、而不是停在建议层面的样子。

视觉维度更难，因为你描述的是**渲染出来的结果**，不是文字。办法是把
改动锚到一个**可量化的目标**上，而不是一个形容词：

<CodeBlock
  title="视觉维度的 Change 写法"
  language="text"
  code={`# 间距——太挤
Hero 看着挤。把标题、副标、CTA 之间的垂直间距分别加到 24px 和 32px。
其他一律不动。

# 颜色——CTA 和主色打架
CTA 在和标题抢注意力。把 CTA 改成主色满饱和度，把标题压到配色里的
墨色。其他一律不动。`}
/>

「太挤」不是一条 Change，「把间距加到 32px」才是。**目标越可量化，
模型要猜的 diff 就越小**。

## 一轮只改一处

一旦你掌握了后续的形状，就会想打包：副标**和** CTA 颜色**和**间距，
一个 Prompt 全修了。忍住。

<Callout tone="warn" title="打包修改，你就丢了 debugger">
  当你一次要三处改动、结果反而更糟时，你没法判断是这三条指令里的哪
  一条造成了倒退。一轮只改一处，能让每次迭代都**可归因**——你永远清
  楚到底动了什么。感觉上更慢。实际上快得多，因为你永远不用去拆一团
  多处改动搅在一起的乱麻。
</Callout>

## 后续之后的验收

模型不会给你一个 diff——它会**把整个文件重写一遍再返回**，哪怕你只让
它动一行。所以你**不是**在核对「逐字节相同」：那几乎永远不成立，去追
它只会把你打回重摇的循环。你核对的是锚点**读起来、看起来是不是一样**。
拿眼睛过一遍：

<Checklist
  storageKey="saas-landing-step-03-output"
  title="这次后续真的成了吗？"
  items={[
    { id: 'fixed', label: '你点名的那一处，现在修好了' },
    { id: 'headline', label: '标题读起来一模一样——同样的词、同样的意思' },
    { id: 'cta', label: 'CTA 的文字、样式、位置都没变' },
    { id: 'palette', label: '配色和主色没变' },
    { id: 'layout', label: '布局和间距看着一样' }
  ]}
/>

无关紧要的抖动别管——重新折行、import 换了顺序、引号风格变了。要紧的
是锚点有没有发生**你看得见、读得出**的变化：标题被重新措辞了、按钮挪
位了、主色偏了。只要有一处，这次后续就**失败了**——哪怕它看着像进展。
用更硬的 Keep 块重跑，或者回退、把那一条 Change 写得更紧。**不要接受
一个悄悄碰坏了锚点的修复**；这笔债会在后面每一个 section 上滚雪球。

## 为什么这个结构能复用

**Keep / Change** 这个结构，是 step 02 那个 **角色 / 决定 / 任务 /
约束 / 输出** 的迭代版对应物。每次你去碰一个已经大体对了的 section
——pricing、FAQ、step 04 的 feature grid——你都伸手去拿同样这两块：锚
住对的，点名唯一的改动，框住 diff。

这一步真正在练的技能**不是**「迭代 AI 产出」，而是**框住爆炸半径，让
每次迭代永远只动一处**。
